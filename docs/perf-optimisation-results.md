# ace-jax speed-ups: results

This page is generated by `bench/scaling/perf_results.py` from this template
(`bench/scaling/perf_results_template.md`); every table is computed from the
committed rows. The spec is `docs/perf-optimisation-spec.md`.

The branch makes these changes, for both `PACEModel` and `ACEModel` where they
apply:
- the calculator reuses its neighbour list within a 1 Å skin, in one compiled
  step;
- evaluation is chunked over atoms;
- forces come from a reverse-edge gather instead of a scatter;
- the SBessel radial uses a recurrence;
- PACE builds A pool-first, and ACE's product basis is feature-major;
- the LAMMPS bundle evaluates owned atoms' rows only.

Sources:
- **Micro-benchmarks:** `bench/perf/results/microbench_{before,after}.json`.
- **Scaling suite, after:** `bench/scaling/results/*.jsonl`.
- **Scaling suite, before:** `bench/scaling/results/before-perf/*.jsonl`.

Cantor medium, float64, A100, 8,192 atoms.

| criterion | target | before | after | verdict |

| model call, calculator-level incl. host-device traffic | ≤ 4.5 ms | 7.25 ms | 5.44 ms | **missed** |
| end to end (micro-benchmark) | ≥ 1.10M atom-steps/s | 275k | 1.29M | **met** |
| end to end (scaling suite, standalone) | ≥ 1.10M atom-steps/s | 346k | 1.58M | **met** |
| LAMMPS throughput | ≥ 1.00M atom-steps/s | 450k | 968k | **missed** |
| LAMMPS runs at 32,768 atoms | runs | ran (dense), 331k | ran (dense), 1.11M | **met** |
| LAMMPS runs at 131,072 atoms | runs | ran (sparse), 212k | ran (dense), 891k | **met** |
| LAMMPS largest N (for information) | — | 262144 | 262144 | — |

- **Model call:** met like for like. The calculator-level time misses the
  target because it includes copying positions to the GPU and results back
  on every call. Both numbers are reported.
- **End to end:** met, in both the micro-benchmark and the scaling suite.
- **LAMMPS:** narrowly missed on throughput. The larger sizes run, now with
  the dense layout.
  - The suite's before rows already reached both sizes, but 131,072 only
    through the slower sparse fallback.
  - The spec's out-of-memory at 32k atoms came from the profiling harness
    (`docs/pace-performance-gap.md` §9), not from these rows.
  - The likely contributor is slot sizing. lammps-jax passes LAMMPS's whole
    neighbour list, skin included, so the bundle's slots are sized for
    rcut + skin, about 1.7× the in-cutoff need.
  - The model therefore does work for pairs beyond the cutoff. This has not
    been measured separately.

## Scaling suite

Float64 throughput in atom-steps/s at the host's fixed size (8,192 atoms on a
GPU, 2,048 on the CPU):
- **before / after:** ace-jax before and after the speed-ups;
- **ML-PACE:** in LAMMPS on the same system and size, for reference;
- **largest N:** the largest size that ran on the ladder. The ladder stops at
  2,097,152 atoms on the A100, 1,048,576 on the A4500 and 32,768 on the CPU.

"—" means the line didn't run at that size, usually because it ran out of
memory.

The standalone method changed with the speed-ups:
- the rows before rebuild the neighbour list on every call;
- the rows after are MD-like: atoms are moved slightly between calls, and the
  list is reused within its skin.

The neighbour reuse is part of what the branch delivers.

## Findings: two bugs in the LAMMPS bundle

The Task 7 bundle changes had two bugs, which only real LAMMPS runs revealed.

- **Bundle key collision.**
  - The export recorded the owned-row count as `ace_jax.max_owned`.
    lammps-jax reads a `max_owned` key anywhere in the bundle as its own, so
    LAMMPS refused every ace-jax bundle.
  - The fix renames it `ace_jax.owned_rows`, with a test against all
    lammps-jax contract keys.
  - The tests that need lammps-jax skip in an environment without it, which
    is why they missed this. CI should install lammps-jax.
- **Slot sizing.**
  - The slots were sized for rcut alone, on the belief that lammps-jax drops
    pairs beyond the cutoff. It doesn't, so the A100 runs overflowed ("edge
    capacity exceeded").
  - The fix sizes them for rcut + skin, and still counts owned rows only.
